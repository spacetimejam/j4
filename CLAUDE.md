# j4: job-search kit

A kit for running AI-assisted job searches. The repo (the "kit checkout") holds templates and shared services; each job-seeker gets their own project folder created by the setup wizard, conventionally a sibling directory named after their initials.

## Layout

- `setup/`: wizard (`setup.sh` + `lib.sh`, bash 3.2 compatible; `jawbs-local.sh` sets up Jawbs in the browser on the person's own computer) and its test harness `setup/test/run-tests.sh` (plain bash, prints `Passed: N  Failed: N`). Run after any setup change.
- `template/`: files copied into each new project (CLAUDE.md.tmpl, tracker/, WORKFLOW.md, ...). Placeholders are `{{TOKEN}}`, substituted by `substitute_all` in `setup/lib.sh`.
- `portal/`: shared submission portal (Node 18+, Express, better-sqlite3, `npm test` uses node:test). One instance runs from the kit checkout and serves every project folder; it can also run locally for one person (`EXPOSURE=local`).
- `docs/superpowers/`: specs and plans. `docs/design-private/`: dated historical design records (do not update for later changes).

## Key decisions: don't re-litigate

- **One person per portal login; no helper mode.** A helper uses Claude Code CLI in the person's project folder, never the portal. Do not add any "view another user's sessions" feature (owner decision, 2026-07-14).
- **Shared portal, registry-based users.** `portal/data/users.json` (gitignored) maps lowercased email → `{name, projectDir, admin?}`; re-read on every lookup, so edits need no restart. The wizard registers users on `PORTAL=yes`; it no longer copies `portal/` into projects.
- **File-based tracker only.** `tracker/applications.csv` is the single source of truth; the grist option was removed 2026-07-14. If readability becomes an issue, generate views from the CSV rather than switching backends.
- **No mascot.** The capybara mascot experiment was judged a failed test and fully rolled back (owner decision, 2026-07-19). Do not reintroduce it.
- **Portal reply directives.** Agent replies may end with fenced blocks the queue strips and acts on: `session-title` (renames the session; sits before any email block) and `email-to-user` (sends deliverables). Parse order in `queue.js` is email first, then title on the cleaned text. `parseEmailDirective`/`parseTitleDirective` strip the last matching block wherever it sits and keep any text before *and* after it, so a Sources/citations section the agent appends after the block no longer leaves the JSON visible or the directive unapplied (they used to be anchored to the very end). The `session-title` block also carries `awaiting_user`, and `sessionStatus` in `queue.js` derives the session status from it: the Reply badge means "Claude asked something still outstanding", not "Claude stopped talking", so a turn that ends the exchange or leaves the next move with an employer goes to `active` instead of `awaiting_reply`. When the agent omits the field the old behaviour stands (`awaiting_reply`), because a silently missing badge hides a real question. A failed resume retries once in a fresh session with `buildRecoveryPrompt` context. Specs: `docs/superpowers/specs/2026-07-19-portal-session-titles-design.md`, `2026-07-19-portal-resume-fallback-design.md`.
- **The reply is a schema field, not text the portal has to identify.** `runClaudeSdk` passes `REPLY_SCHEMA` (in `reply-schema.js`, re-exported from `agent.js`; it sits in its own module so `agent.js` and the runners do not import each other) as the SDK's `outputFormat`, and the turn returns `{reply, title, awaiting_user, email}` in `structured_output`. `queue.js` reads those fields directly, so nothing the agent narrates while working can reach the user and there is no rule for deciding which text is the answer. An empty `reply` throws, which routes to `needs_attention` plus an admin email, and the guard sits below the structured/fenced branch so it covers both: the failure it replaced was silent on either path. On 2026-08-12 the agent answered Sam, edited the tracker, closed with a bare `session-title` block, and the portal stored an empty message while marking the job `done`. The fenced fallback is for `runCli` and `runCodex` only, and `portalPrompt` gives them the fenced protocol while schema-capable runners in `STRUCTURED_RUNNERS` get the field descriptions. A schema-capable runner never falls back: `runClaudeSdk` throws when a successful turn carries no `structured_output`, because that agent was prompted with the structured protocol and its text holds no fenced blocks either, so parsing it would title nothing, send nothing and badge every session for a reply while the portal looked healthy. `outputFormat` support was verified at `@anthropic-ai/claude-agent-sdk` 0.3.207. The floor in `package.json` is now 0.3.283, because Opus 5.5 (the default model since 2026-09-27) needs the Claude Code 2.1.280 or newer that it bundles; older versions fail every turn with a 400. The remaining risk is that the whole markdown reply travels as an escaped JSON string, so watch the first live turns for flattening. Spec: `docs/superpowers/specs/2026-08-12-portal-single-answer-replies-design.md`.
- **Archive then delete.** Portal applications are archived off the list first; permanent delete works only on archived sessions, removes the derived `applications/<slug>/` folder (realpath-validated, delivered-files paths only), and appends a record to the project's `applications/DELETED.md`. Spec: `docs/superpowers/specs/2026-07-19-portal-archive-delete-design.md`.
- **Markdown rendering, Claude's replies only.** `portal/public/markdown.js` renders Claude's messages as rich text; user messages keep `esc()` and `white-space: pre-wrap`, so a pasted job description is never reformatted. The renderer is dependency-free and XSS-safe by construction: it escapes all text first, emits only its own tags, and allows only `http`/`https`/`mailto` hrefs. Keep it that way, because `express.static` serves the portal with no CSP, so the renderer is the only defence against markup in fetched job listings that Claude quotes back. `app.js` is an ES module for this reason (`index.html` loads it with `type="module"`). Tables and nested lists are deliberately out of scope. Spec: `docs/superpowers/specs/2026-07-20-portal-markdown-rendering-design.md`.
- **Keyboard submit.** Cmd+Enter (macOS) or Ctrl+Enter submits both portal textareas, via `isSubmitChord` in `portal/public/keys.js` and `bindSubmit` in `app.js`. Plain Enter stays a newline in both boxes, deliberately: the new application box receives pasted multi-line job descriptions. `bindSubmit` also guards against double submits. Spec: `docs/superpowers/specs/2026-07-20-portal-keyboard-submit-design.md`.
- **Attachment names are normalised for Brevo.** Brevo rejects `.md` attachment filenames ("Unsupported file format: md") and 400s the entire send, so `normaliseAttachments` in `portal/src/email.js` renames `.md` to `.txt` for every provider, before the retry loop. Do not push this down into a single provider: it lived in `sendViaBrevo` alone until 2026-07-21, while production runs `EMAIL_PROVIDER=webhook`, so interview prep emails failed with `webhook responded 500` even though the chat itself worked. The n8n "Build Email Payload" node carries the same rule for anything reaching Brevo by another route; keep the two in step. `.yaml` is unsupported by Brevo too, and is not handled because nothing currently attaches it.
- **UTC in the database, London on screen.** Timestamps are stored as UTC (`datetime('now')`) and never converted at rest: UTC sorts correctly and never repeats an hour. `formatLondon` in `portal/public/time.js` renders them in `Europe/London` at display time, so BST and GMT are handled by the zone data rather than a fixed offset, and the zone is pinned rather than taken from the browser so the portal reads the same abroad. The trailing `Z` in that function is load-bearing: SQLite's `YYYY-MM-DD HH:MM:SS` has no zone marker and `Date` parses that shape as local time, which would look correct on a UTC host and be wrong everywhere else.
- **Delivered documents accumulate; `files` does not.** `sessions.files` holds only the most recent delivery, because `deriveApplicationFolder` in `portal/src/deletion.js` reads `files[0]`. The history lives in the `documents` table, appended by `queue.js` on every `email-to-user` directive and unique per `(session_id, path)`, so a redelivered file updates one row rather than adding a second pointing at the same bytes. The one-time backfill in `getDb()` is guarded by a `documents_backfill_done` row in `meta`, not by a row count: an empty `documents` table is also what deleting every row looks like, so a count-based guard would resurrect them from `files`. In the UI, the panel mounts on `document.body` rather than inside `#app`, and `refreshDocPanel` compares against remembered markup rather than reading `innerHTML` back: the ten-second poll while a session is `working` rewrites `app.innerHTML`, and a read-back comparison never matches because `download` re-serialises as `download=""`. Spec: `docs/superpowers/specs/2026-07-21-portal-document-panel-design.md`.
- **Inline document footers.** Documents appear as download chips at the foot of the Claude message that delivered them, rather than in a standalone card above the reply box. The `documents.message_id` column links each document to its message; the side panel remains as the single-place-to-find-everything view. `session.files` is retained for `deriveApplicationFolder` but the frontend no longer reads it. Spec: `docs/superpowers/specs/2026-08-03-portal-inline-document-footers-design.md`.
- **The status pill shows application stage, not conversation state.** The pill reads where the application stands in `tracker/applications.csv` instead of prose about what Claude just did, except while a turn is running, when `working` overrides it; the reply prompt that used to live in the pill text moved to a red corner badge so the two stop competing for one element. `stageFor` in `portal/src/tracker.js` matches a session to a tracker row by its `<Role> at <Org>` title, splitting on the last ` at ` and matching the org by prefix in either direction, so "... at M+C Saatchi" still finds "M+C Saatchi UK". Legacy Status values stay in the `STAGES` map so an existing CSV keeps reading correctly; an unrecognised value renders no pill rather than a wrong one. `inactive` is derived at display time from `INACTIVE_DAYS`, not stored. The stage 3 trigger in `agent.js` now keys off the tracker row's `Date_Applied` being filled in, not a Status comparison, because `Applying` spans both sides of sending. Spec: `docs/superpowers/specs/2026-07-21-portal-application-stage-pills-design.md`.
- **Voice notes are built from the intake conversation, not held back for a writing sample.** `template/core/voice.md` used to say "ideally from samples of the user's own writing", which in practice left the file empty and every draft in the AI's default register, because the old cover letter rarely turns up (owner decision, 2026-08-09). The intake transcript is the richest sample most projects will ever have and it exists in session one. The method is in that file's header: split durable traits from spoken-only artefacts (verbal hedges, fillers, fragments) and write both lists explicitly, so a later session can tell which is which. Writing samples remain better evidence about *written* register; they are a revision, not a precondition. The "one warm letter is a register, not a licence" caution in the same file is about how far a sample licenses informality, not about which sources are admissible; the two are noted as compatible in place.
- **One shared sign-off bank, no per-project lists.** The email sign-off list lives once at the kit root (`email-sign-offs.md`) and every project reads it there; the template no longer ships a copy, because four copies drifted apart (owner decision, 2026-08-04). There is deliberately no per-project override or extras file: the entries worth keeping from the one list that had diverged were merged into the shared bank instead. Project spine files carry the resolved picker command, substituted from the `{{KIT_DIR}}` token in `substitute_all`, so a project created outside the kit root still finds the bank.
- **A usage limit is a notice, not a fault.** When the Claude account's usage limit stops a turn, `runClaudeSdk` throws `UsageLimitError` (`portal/src/usage-limit.js`), taking the reset time from a rejected `rate_limit_event` when one arrived and otherwise estimating it from the error text ("resets 12:10am (UTC)"). `queue.js` records it on the job (`failure_kind`, `resets_at`, `resets_at_exact`, `limit_type`), sets the session to `usage_limited`, skips the fresh-session recovery (it would hit the same limit) and sends no admin email. The page shows the reset in UK time and a Retry button that requeues the same job, so the message is not duplicated. Retry is manual only and always pressable (owner decision, 2026-09-27). Spec: `docs/superpowers/specs/2026-09-27-portal-usage-limit-notice-design.md`.
- **ChatGPT writes the CV and cover letter copy; Claude briefs and checks it.** In the portal, stage 2 and redrafts have Claude write `brief.md` and run `bin/chatgpt-draft` (logic in `portal/src/drafting.js`), which calls `codex exec` read-only in the project folder with GPT-6 Astra at low effort on the ChatGPT subscription signed in on beep, and writes `draft.json` plus `draft-provenance.json` (model, effort, Codex version, brief and draft hashes). CV copy comes back as sections named after the fields in that project's own `render/templates/configuration.yaml`, because CV layouts differ between projects. Claude may fit, cut and fact-correct the copy but not rewrite it; `gaps` become questions for the user. When the writer is unavailable the draft waits, never substituted (owner decision, 2026-09-28): the agent sets `drafting_blocked` in `REPLY_SCHEMA`, the session goes to `drafting_blocked` with a Retry button that requeues the job with a carry-on prefix, and admins are emailed for `auth` and `error` but not a limit. Fix an `auth` block with `codex login` as the service user. The queue also emails admins when a CV or letter is delivered from a folder with no provenance newer than its brief, so a bypass is visible. `--ignore-user-config` keeps the owner's MCP servers away from the writer, and stdin must be closed or `codex exec` hangs. Only `STRUCTURED_RUNNERS` get this; Claude Code sessions in a project folder still draft as before. Spec: `docs/superpowers/specs/2026-09-28-portal-chatgpt-drafting-design.md`. This is the `SUBSCRIPTIONS=both` default. A host with one subscription opts out explicitly in `.env` (`claude-only`, where Claude drafts as before and the provenance alert is off, or `chatgpt-only`, which needs `AGENT_RUNNER=codex`); nothing falls back on its own. Preflight refuses to start under `both` when Codex is not installed, but only warns when it is signed out, since logins lapse and a refusal would turn a restart into an outage (owner decision, 2026-09-28). `draftingEnabled` in `agent.js` is the one switch the prompt and queue share. Spec: `docs/superpowers/specs/2026-09-28-portal-single-subscription-design.md`.
- **Jawbs on your own computer has no sign-in.** `EXPOSURE=local` serves the one registered user without a cookie (`requireAuth` in `auth.js`), binds loopback only, and preflight refuses to start with any other bind, more than one user, or a non-localhost `BASE_URL` (owner decision, 2026-09-28, chosen over a launcher-minted login link). `localHostGuard` in `portal/src/local.js` is load-bearing, not hardening: with no sign-in, a Host check on every route (static files included) plus an Origin check on writes is the only thing stopping DNS rebinding from letting any website drive the agent. The wizard's option 1 runs `setup/jawbs-local.sh`, which writes `portal/.env`, registers the user and installs `bin/jawbs-open` (generated, gitignored, with node and PATH baked in because GUI launches do not get the login shell's PATH) plus icons. One local person per kit checkout; each checkout picks its own free port (8710 upwards), and the launcher only trusts a Jawbs whose `/api/meta` names its own kit. With no sign-in, anyone with an account on the computer can reach it, so it suits a computer only one person uses. Spec: `docs/superpowers/specs/2026-09-28-jawbs-local-mode-design.md`.
- **Signed-out Claude is a notice, not a fault.** `runClaudeSdk` throws `SignInError` (`portal/src/sign-in.js`) when an assistant message is marked `authentication_failed` or the text says "Not logged in". `queue.js` sets the session to `signed_out`, skips the fresh-session recovery (every session shares the one sign-in), and still emails admins, because on a shared portal only the owner can fix it. The page shows a Try again notice: on your own computer it gives the `claude auth login` steps, on a shared portal it says the owner has been told. `jawbs-local.sh` checks `claude auth status` and offers the browser sign-in when run in a terminal, but never stops setup over it.
- **The writer is the person's choice on their own computer.** The wizard's option 1 asks who writes CVs and letters (`both`, recommended; `claude-only`; `chatgpt-only`) and records it in SETUP.md as `Writer:`. `jawbs-local.sh` follows it rather than guessing from what is signed in, checks only the programs the choice needs, and writes `AGENT_RUNNER=codex` for `chatgpt-only`. Chosen `both` with Codex missing asks whether to stop or let Claude write; it never switches on its own. Projects from before the question (`Writer: detect`) still detect. The shared portal and terminal mode are not asked (owner decision, 2026-09-29). Locally, a writer signed out names ChatGPT and gives `codex login`, the one exception to the unnamed-vendor rule.
- **Career-step interviews.** Setup opens by saying Jawbs is only as good as what the person shares, and session B interviews each role in the master CV, most recent first, skippable. The questions and where answers go live once, in `template/core/intake.md` "Career-step interviews"; each role in `master-cv.md` ends `Interviewed:` or `Skipped by choice:`. After setup, the spine and `portalPrompt` run one on request, titled "Career interview: <role>, <organisation>" (a comma, so `stageFor` never matches it to a tracker row).
- **Intake can run in the portal.** A session with `kind = 'setup'` ("Getting started") works through the project's `SETUP.md` with `setupPrompt` in `agent.js`; setup is pending exactly while `SETUP.md` exists, so the portal stores no progress. While pending, the landing page is that conversation and the new application box is hidden. Uploads (`POST /api/sessions/:id/upload`, setup sessions only, 15 MB, document types) land in `core/source/`. The kit now ships a default CV and letter template (derived from vantage-cv, MIT) so session C renders without a template choice.
- **CV designs come from Typst Universe's CV category, and only there.** Session C offers the category link (https://typst.app/universe/search/?kind=templates&category=cv) before and after the test CV in `applications/test-render/`, and after setup the cog menu's "Change CV design" opens a `kind = 'design'` session ("CV design", one open per person, `designPrompt`). Three project scripts hold the rules so a prompt cannot bend them: `render/fetch-template.py` refuses anything that is not a template in the `cv` category, `render/try-design.sh` proves a candidate against `render/sample/` and the test CV (CV one page, letter passes its own fill guard) without touching live files, and `render/switch-design.sh` switches only after that, keeping the old design in `render/templates-previous/`. The yaml content model never changes, so ChatGPT drafting and existing applications keep working; the letter matches the CV where it can. The adaptation procedure lives once, in `template/render/README.md` "Adapting a template" (owner decision, 2026-09-29). Spec: `docs/superpowers/specs/2026-09-29-cv-design-picker-design.md`.

## Constraints

- Setup scripts stay bash 3.2 compatible: no associative arrays, no readarray, no `sed -i`, no `${var,,}`, no GNU-only flags.
- Setup must never fail when node is absent (`register_portal_user` prints manual instructions and returns 0).
- Setup tests must never write the real registry: always set `PORTAL_REGISTRY` in tests.
- SETUP.md portal task text must keep the literal phrase "If you chose the portal" (tests grep for it).
- Docs: no em/en dashes as sentence punctuation.
